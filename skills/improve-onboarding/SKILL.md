# Improve onboarding

Help a new user experience the product's value with enough context to make informed choices. Optimise for reaching value, not the fewest screens. Signup completion alone is not activation.

## Define the useful outcome

Establish the intended audience, acquisition promise, first useful result and prerequisites. Inspect existing product documentation, journey and available data before inventing an activation event. Use a provisional definition if needed and label it as such.

Separate users with different needs when it changes the journey: new versus returning, invited versus self-serve, or starting from an example versus a blank state. Do not add segmentation or personalisation steps without a purpose.

## Walk through the journey

Follow the relevant path from entry page to the first meaningful result, including signup and setup where they belong. Do not assume account creation must come first. Include mobile, slow or failed requests, empty data, interrupted sessions and resuming where relevant.

- Judge each step by whether it helps the user experience value, enables necessary setup or resolves consequential uncertainty. Remove steps without a useful purpose; preserve worthwhile effort even when the resulting flow is longer.
- Match the acquisition promise to what the product delivers next. Avoid a tour that delays the outcome or sends people into unrelated educational content.
- Consider a working example, interactive preview or first real task instead of introductory feature slides. Where practical, let users experience value before signup and preserve their work when they create an account.
- Ask only for information necessary at that point. Explain consequential choices and provide sensible, reversible defaults without silently choosing a user's interests.
- Make personalisation pay off. Show how answers affect the result, recommendations or setup. Remove questions that do not meaningfully change the experience; a quiz is not inherently valuable.
- Reveal complexity when it becomes useful. Give help where the user needs it rather than adding an introductory step for every feature.
- For meaningful multi-step setup, consider contextual guidance or a checklist tied to real tasks. A simple utility may need neither a tour nor a checklist.
- Show progress through actual work when there is a meaningful endpoint: for example, "Step 2 of 4". Use percentages or time estimates only when justified, including branching paths. Setup completion is not proof of learning or activation. Explain real processing during necessary waits; do not manufacture delays, checks or completion badges. Make loading or error states recoverable.
- Give a useful first outcome a clear ending: explain what happened, what was saved and the next action. Match acknowledgement to the actual achievement; do not claim mastery or add celebration by default. Fix frustrating steps rather than relying on a positive ending to compensate.
- Request permissions when the benefit becomes clear. Explain the immediate use and, when helpful, preview the actual notification or outcome before the system prompt. Do not add a generic permission pre-screen by default; respect refusal and keep optional access optional.
- Explain pricing, free-access limits and what happens next at the appropriate decision point. Avoid surprise charges, misleading scarcity and cancellation obstruction.
- Check authentication redirects, profile provisioning, saved choices and access gates where they affect the path. A new user should not be treated as expired simply because setup is incomplete.

Do not remove productive effort that constitutes the product's value. For example, explaining an idea may be the learning activity itself; making the answer effortless could weaken the result.

Founder notes, animation, multiple-goal selection, split forms and personalised previews are optional tactics. Recommend one only when it serves this audience and task. Do not copy another app's flow length or assume broad regional stereotypes establish a user's interface preferences.

## Use evidence carefully

Use authorised funnels, recordings, interviews or support reports when supplied. Define the time window, cohort, event denominators and device or channel differences. Distinguish observed abandonment from its suspected cause; a click rate alone does not explain user intent.

If evidence is limited, explain the heuristic finding and propose a small way to test it. Do not claim a conversion uplift before observing one. Case-study percentages and screen-count averages need their original source, sample and measurement context before being used as evidence; they are not targets or portable forecasts.

For the rationale and limitations of the onboarding examples that informed these additions, see [references/learning-notes.md](references/learning-notes.md). Read it when tracing a recommendation or evaluating whether an example supports a proposed rule.

## Recommend and verify

Describe the concrete obstacle, proposed change and why it should help the first useful outcome. Prioritise changes the user can act on. Evaluate activation, retained use and paid conversion together where relevant. An increase in purchases is not sufficient evidence of success if useful outcomes or retention decline; consider refunds and complaints when assessing a paywall change. State which outcomes are measured and which remain unknown.

For implementation, preserve existing account data and resume behaviour. Test the affected path and its important failure state with authorised or synthetic accounts. Separate review findings, implemented changes and measured results.
